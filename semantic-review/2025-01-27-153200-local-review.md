# Deliverables view, Slate grouping, team title field, and Stripe lookup-key resolution

This diff adds a third "Deliverables" view to the project board, enriches the deliverable detail page with an accordion layout and edit modal, introduces multi-axis grouping to the Slate page, adds a `title` field for team members, refactors Stripe price resolution to prefer lookup keys over product-name guessing, and seeds new entities (packages, sessions, stage-tasks). The rename from "Editor" to "Crew" in i18n touches a user-visible role label. The auto-accept invite flow in `auth.ts` is also new — on login, pending invites are accepted silently so the user lands in the workspace immediately.

Watch for: SlatePage's `groupedByClient`/`groupedByProject` computeds duplicate the exact same grouping logic and should be extracted (confirmed). The deadline view's "Up next" bucket is narrowed to deliverable-linked backlog tasks only — standalone backlog tasks show under "In progress", which is mislabeled (confirmed). Missing Firestore collectionGroup index for the `my-invites` query will cause a runtime crash (likely).

## High-level view

The project board toolbar was flattened into a single primary "new task" button plus an overflow menu. The new `deliverables` view tab renders deliverables grouped by sub-group, pulling data already loaded by `loadProjectDeliverables`.

The deliverable detail page now uses an accordion with expand/collapse per stage, a detail panel showing assignee/status/due, and an edit modal for name + metadata. The orgId filter added to the task query is a correctness fix — Firestore security rules reject queries that don't scope to the org.

Slate adds a `SegmentedControl` for deadline/client/project grouping. The two non-deadline computeds are structurally identical and extractable. The `load()` function now calls `loadAllProjects()` unconditionally — an extra round-trip that only matters for the project view.

Stripe price resolution gained a two-tier strategy: lookup keys first (deterministic), then product-name heuristics only for unfilled slots. The billing checkout endpoint now fails early with 503 `price_unavailable` instead of sending an empty `price` to Stripe. The invite auto-accept fires `Promise.allSettled` for all pending invites, with no UI feedback on partial failure.

## SlatePage grouping logic repetition

`groupedByClient` and `groupedByProject` share identical structure: build a `Map<string, Task[]>` keyed by a field, then map entries into `{ key, label, tasks }`. The only differences are the field accessor (`tk.clientId` vs `tk.projectId`) and the label resolver (`data.getClient` vs `data.getProject`). A helper like:

```ts
function groupTasksBy(
  keyFn: (tk: Task) => string,
  labelFn: (key: string) => string,
): TaskGroup[] {
  const map = new Map<string, Task[]>()
  for (const tk of myTasks.value) {
    const key = keyFn(tk) || '_none'
    if (!map.has(key)) map.set(key, [])
    map.get(key)!.push(tk)
  }
  return [...map.entries()].map(([k, tasks]) => ({ key: k, label: labelFn(k), tasks }))
}
```

would eliminate the duplication and make future groupings trivial to add.

## Accordion: `taskForStage()` called N times per stage

In the `DeliverableDetailPage` template, `taskForStage(stage.id)` is invoked for: the pipeline dot color, the status badge, the "no task" label, and inside the expanded panel for assignee/status/due/description/link. That's 5-7 linear scans per stage per render cycle. Replace with:

```ts
const taskByStage = computed(() => new Map(stageTasks.value.map((t) => [t.stageId, t])))
```

## Missing collectionGroup index for `my-invites`

The new `GET /orgs/my-invites` endpoint queries:

```ts
db.collectionGroup("invites")
  .where("email", "==", email)
  .where("status", "==", "pending")
```

The `firestore.indexes.json` additions in this diff are for the `tasks` collection, not `invites`. A collectionGroup query with two equality filters on different fields requires an explicit composite index. Without it, the query throws `FAILED_PRECONDITION` at runtime. Add:

```json
{
  "collectionGroup": "invites",
  "queryScope": "COLLECTION_GROUP",
  "fields": [
    { "fieldPath": "email", "order": "ASCENDING" },
    { "fieldPath": "status", "order": "ASCENDING" }
  ]
}
```

## Invite auto-accept: partial-failure gap

`checkAndAcceptInvites` uses `Promise.allSettled` and clears `pendingInvites` wholesale if any one invite succeeds. If the user had 3 pending invites and only 1 accepted (others revoked or expired between fetch and accept), the UI shows nothing about the failed two. The manual invite-link fallback still works, but the user has no signal that they missed invitations.

## "Crew" not translated in Spanish

```ts
// en
contractor: 'Crew',
// es
contractor: 'Crew',
```

Every other role has a Spanish translation. If "Crew" is a brand term meant to stay English across locales, add a comment. Otherwise use `'Equipo'` or `'Colaborador'`.
