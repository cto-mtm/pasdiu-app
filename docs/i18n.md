# i18n Cookbook

vue-i18n in Composition API mode (`legacy: false`). **`en` is the source of truth**; `es` is the fallback and is typed against `en`. Setup lives in `src/i18n/index.ts`.

Strings live in **per-feature TypeScript modules**, not in monolithic JSON. Each module co-locates both locales and types `es` against `en`, so a missing or extra key in either language is a **compile-time error** — not a runtime warning.

## Structure

```
src/i18n/
├── index.ts                 # assembles modules, builds messages, type augmentation
└── locales/
    ├── configs/             # cross-cutting vocab (common)
    ├── components/          # component-scoped strings (shell, …)
    └── pages/               # page/route-scoped strings (dashboard, client, board, settings, …)
```

The folder is organizational only. Each module registers under its **namespace key** (the file name), so keys stay `t('dashboard.title')` regardless of folder.

## Module format

```ts
const en = {
  title: 'Items',
  empty: 'No items',
}

// Typed against en: a missing or extra key here is a compile error.
const es: typeof en = {
  title: 'Elementos',
  empty: 'Sin elementos',
}

export default { en, es }
```

`en` is the source of truth. Because `es` is typed `typeof en`, you literally cannot ship a namespace where the two locales diverge — TypeScript rejects it.

## 1. Add a translated string

1. Open the module for that feature (e.g. `locales/pages/dashboard.ts`).
2. Add the key to **both** `en` and `es` in the same edit. If you forget one, `tsc` fails on `es: typeof en`.
3. In the component: `const { t } = useI18n()` then `t('dashboard.key')`. Keys autocomplete from the schema.

Never options-API `$t`, never a hardcoded user-facing string in a template or store.

> Type-safety note: `en`↔`es` key parity is enforced at compile time, and key **autocompletion** works (via the `DefineLocaleMessage` augmentation in `index.ts`). However, vue-i18n keeps a permissive `t(key: string)` overload, so an outright typo in a `t()` call is *not* a `tsc` error — vue-i18n's missing-key console warning is the dev-time backstop for that case.

## 2. Add a new namespace

1. Create `locales/<folder>/<name>.ts` exporting `{ en, es }` in the format above.
2. In `index.ts`, import it and add one line to each of the `en` and `es` blocks of `messages`. (If the namespace collides with a JS reserved word like `import`, alias the binding — e.g. `import importMessages from './locales/pages/import'` — but keep the registered key unchanged.)

## 3. Add a new locale

1. For every module, add the new locale alongside `en`/`es`, or restructure the `{ en, es }` exports to include it. Diff against `en` to translate everything.
2. Add the code to `SUPPORTED_LOCALES` and the `messages` blocks in `index.ts`, and to `datetimeFormats`.

## 4. Translate data (not just UI chrome)

App-owned enum values are stored raw and rendered through keys: task statuses resolve via `t('status.' + status)` (`locales/configs/status.ts`) and member roles via `t('roles.' + role)` (`locales/configs/roles.ts`). Content typed by end users (client names, task titles, metadata) is user data — it is NOT translated.

## 5. Dates, numbers, currency

Use `d(date, 'short')` / `n(value, …)` from `useI18n()` — never hand-format. Store times in UTC and render in the local timezone. Careful with `@` in messages — it's the vue-i18n linked-message marker and must be escaped as `{'@'}`.

## The rules

Every user-facing string is a key in a per-feature module, present in both `en` and `es`. Adding a string = both locales, same commit, enforced by the type system. Data stays translatable via keys. `LocaleSwitcher.vue` flips the global locale.
